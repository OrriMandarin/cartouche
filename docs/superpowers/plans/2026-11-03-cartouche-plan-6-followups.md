# Plan 6 — Follow-ups

Decisions taken while writing the plan 6 spec and plan (the design milestone), then decisions taken during execution and minor findings raised by the reviews and not fixed. The owner approved the brief's decisions (header video without transcoding, kept originals with server-side crops, neutral page in 404, `datetime` field type, Classique icons layout, the design's themes with an id migration and a server-side contrast check, configurable contact points, access-code screen, GDPR checkbox); every other point was decided here, written as a numbered rule and recorded below. To be triaged by the `planner` in later plans.

Each ruling line: decision — reason — cost if wrong. Rulings marked **(changes implemented behaviour)** modify something plans 1 to 4 already shipped or specified.

## Rulings taken (spec/plan phase)

- Ruling R-S1: a header video keeps its file as uploaded (MED-004); its crop rect, loop `{start, end}` and poster time are stored with the media (MED-028) and applied at display time: CSS sizing and offset of the `<video>` inside the 4:3 header for the crop (MED-032), a `timeupdate` handler for the loop, no `loop` attribute — owner decision (no ffmpeg in v1); CSS cropping costs nothing on the server — cost if wrong: a cropped-out area is still downloaded by visitors (the whole file), and a transcoding step later would make these fields its input.
- Ruling R-S2: the "kept original" is a source image: the uploaded image (or a video's whole poster frame) oriented, stripped of metadata and re-encoded in WebP quality 90, longest side ≤ 4,096 px (MED-025); the uploaded bytes are never stored — MED-007 removes EXIF/GPS and plan 2 never stored uploads; 4,096 px leaves a 300 % zoom on a 1,440 px output close to native — cost if wrong: re-crops of very large photos lose detail beyond 4,096 px.
- Ruling R-S3: re-framing creates a new media (new id, copied source and video, newly cut files) through `POST /api/cards/{id}/media/{media_id}/reframe`, attached on the next save like an upload (MED-030) — MED-016 (files never change), EDI-006 (nothing published before saving) and MED-018 (unattached media cleaned on save) all hold without a new mechanism — cost if wrong: a video is copied in storage on each re-frame until the next save deletes the old one (≤ 25 MB, a rare action).
- Ruling R-S4: a source is readable only through a signed address given to the owner (MED-031); `Audience::Dashboard` splits into `Owner` and `Support`, and only `Owner` carries `source` — the source may hold what the owner cropped out on purpose; support's read-only views (ADM-013) do not need it — cost if wrong: support cannot see the uncropped image of a reported card (it sees what the public sees).
- Ruling R-S5: crops are proportions of the source (0–1) with a 1 % shape tolerance and a centered default (MED-026); a loop lasts at least 1 s unless it is the whole video; the poster time lies within the video; field codes `invalid_crop`, `invalid_loop`, `invalid_poster_time`; 50 ms tolerance on durations — the handoff stores proportions; pixel rounding needs a tolerance; a sub-second loop flickers — cost if wrong: one constant each.
- Ruling R-S6 **(changes implemented behaviour)**: new header images and posters are cut to 4:3 and produced at 750, 1,125 and 1,440 px wide in WebP only (MED-015), instead of 640/1,080/1,920 px at the original ratio; no AVIF or JPEG header variant — handoff §7 gives 1,440 × 1,080 with 750/1,125/1,440 variants; the card is at most 28rem (448 px) wide, so 1,440 covers 3× screens; every target browser reads WebP and AVIF would add an encoder dependency; media uploaded before keep their files — cost if wrong: a JPEG fallback or AVIF variant is one more planned variant.
- Ruling R-S7 **(changes implemented behaviour)**: the neutral page "Cette carte n’est pas disponible" is served with HTTP 404 for disabled, deleted and suspended-owner cards **and** for slugs never assigned (LNK-006, LNK-023, LNK-027, LNK-034); the "Carte introuvable" page disappears; the form route reaches the same page through a layout-level `notFound()`, while an unknown event keeps "Formulaire introuvable" (FRM-024) — owner decision (handoff §4: same page, same code); merging the unknown case removes the last difference a visitor could observe — cost if wrong: two 404 pages to tell apart again.
- Ruling R-S8: a `datetime` answer is the naive `YYYY-MM-DDTHH:MM` the browser's `datetime-local` gives, stored as typed, never converted between time zones, rejected with the existing `invalid_date` code (FRM-043); exports and the detail view show it as entered (LEA-033) — owner decision to add the type; the prospect means a wall-clock time at the event's place, and the browser does not tell which zone it means — cost if wrong: a zone column if owners need absolute instants.
- Ruling R-S9 **(changes implemented behaviour)**: the Classique template's only setting is "Disposition des liens", `icons` by default; `animate_events` is dropped and ignored at render (TPL-027) — owner decision for the layout; the design has no animation switch and reduced motion (PUB-038) covers accessibility; cards that stored `links_layout: "list"` keep it — cost if wrong: an owner who had turned animations off sees them again.
- Ruling R-S10 **(changes implemented behaviour)**: the design's 8 themes and 4 pairs replace the placeholders; migration 0007 renames the stored ids (`clair` → `craie`, `sombre` → `encre`, `sable` → `ivoire`, `ocean` → `minuit`, `foret` → `sauge`, `corail` → `terracotta`; `moderne` → `inter`, `editorial` → `playfair`, `chaleureux` → `fraunces`) and pins `font: "inter"` on `ocean` cards without a pair of their own, the only case whose pair would change (TPL-025); render-time fallback kept (TPL-019) — owner decision (plan 2 had said ids would stay; the owner chose the design's ids); colours follow the new theme because a theme is a starting point — cost if wrong: an owner who liked a placeholder palette rebuilds it with overrides.
- Ruling R-S11 **(changes implemented behaviour)**: contrast becomes blocking in the editor (TPL-013) and is enforced by the server on every card save (`400`, `theme`, `low_contrast`, TPL-023); the four checks are those of handoff §3.2, made exact from the design's `contrastChecks` table: the muted text is mixed with the background's **first** colour (as `--c-muted` does), a hovered row is the text at 12 % opacity laid over each background colour, and "accent / fond" is measured against that hovered row (only that reading reproduces the table, every value within 0.1; R-S11's maths is in Task A2); a card stored unreadable still renders, its next save is refused until fixed; duplication is not checked — owner recommendation ("a saved card can never be unreadable"); refusing old cards at render would break public links — cost if wrong: an owner with an old unreadable card must fix colours before any other edit.
- Ruling R-S12: the theme data lives twice, `frontend/web/src/lib/theme/themes.json` and `backend/domain/src/theme/presets.json`, kept byte-equal by a web test — the backend's Docker build context is `backend/` and cannot `include_str!` a file of `frontend/` — cost if wrong: none while the test runs; a generator if a third copy appears.
- Ruling R-S13: the text-on-accent colour (`#FFFFFF` or `#111111`) and the light/dark scheme are computed from the colours at render, never stored (TPL-021, TPL-022) — handoff §3.1 calls `onAccent` "computed at save time"; computing it at render gives the same result for the presets (checked) and needs no migration — cost if wrong: none.
- Ruling R-S14: "Utiliser une couleur lisible" proposes, for the setting concerned (text for checks 1–2, accent for 3–4), the ready-made theme's own value, then `#111111`, then `#FFFFFF`, the first that passes all four checks, and no button when none does (TPL-024) — the mockup proposes the preset's text colour; a deterministic short list is testable — cost if wrong: a smarter colour search.
- Ruling R-S15: brand icons are inline SVG components whose paths are copied from the mockups (lucide's LinkedIn, Instagram, Facebook and YouTube shapes, ISC; Tabler's TikTok and X, MIT), credited in the file (PUB-036) — handoff §4 proposes Simple Icons or Tabler; Simple Icons are filled shapes and would not match lucide's stroke; six paths do not justify a dependency — cost if wrong: swap the six components.
- Ruling R-S16: every `@font-face` of the 8 families is declared globally (fontsource CSS) and browsers download only the files a page uses, so the public page fetches only its pair (TPL-012), checked by an e2e test on the downloaded `.woff2` files; the app font is applied by the `(app)` layout, never on `body`, so that the public page never pulls Inter for nothing — Next's global CSS cannot be loaded per card without a per-pair stylesheet split; the result the handoff wants ("ne charger que la paire") is the bytes downloaded — cost if wrong: a few KB of unused `@font-face` rules on the public page.
- Ruling R-S17 **(changes implemented behaviour)**: the public page follows the design: initials on the accent instead of no avatar, a 128 px accent band instead of the theme background when there is no header, the vCard button right under the identity, a 4:3 header with a mask fade, rows for email and phone, icons layout (PUB-004 to PUB-008, PUB-023, PUB-030 to PUB-038) — handoff §4 — cost if wrong: template CSS only.
- Ruling R-S18: the standard fields stay those of FRM-017 (first name, last name, date of birth, email, phone, postal address); the handoff's list "Prénom et nom, E-mail, Téléphone, Entreprise, Message" is not adopted — FRM-017 is implemented, plan 4's exports are built on it (LEA-023), and "Entreprise" and "Message" are one custom field away — cost if wrong: two more standard fields and an export column change.
- Ruling R-S19: the consent text stays FRM-026's (default) or the owner's custom text; the mockups' short "J’accepte que Camille Roche utilise ces informations…" is sample text — FRM-008 records the exact text as GDPR proof and FRM-026 was written for that — cost if wrong: one default text.
- Ruling R-S20 **(changes implemented behaviour)**: the event form's texts become the mockup's ("Envoyer mes coordonnées", "Tous les champs sont obligatoires, sauf mention « facultatif »", one message per field, the error summary, "Merci {prénom}, c’est envoyé !"), but the confirmation drops "et vous recontactera après le {événement}" (FRM-044 to FRM-047) — "après le" + an arbitrary event title is often wrong French ("après le Portes ouvertes…") and promises a callback the product cannot guarantee; "de" elides to "d’" before a vowel — cost if wrong: one sentence.
- Ruling R-S21: the support address, terms URL and privacy URL are three `NEXT_PUBLIC_*` variables with placeholder defaults (`support@cartouche.invalid`, `/cgu`, `/confidentialite`) documented in `.env.example` (ADM-021) — owner answer to handoff §8; `.invalid` makes a forgotten setting obvious; the two paths are where LND-004's pages will live — cost if wrong: dead links until plan 5 sets them (see "Open points").
- Ruling R-S22: the access-code screen is the form's back link and band (title only, EVT-027), one field "Code d’accès" and the button "Continuer" (FRM-048) — owner answer to handoff §8 — cost if wrong: none.
- Ruling R-S23: the pending-account screen recalls the user's email but does not promise an email ("Tu recevras un e-mail…" in the mockup); it says the account can be used once approved (ACC-026) — Cartouche sends no email (no notification rule, no mail adapter) — cost if wrong: one sentence when approval emails exist.
- Ruling R-S24 **(changes implemented behaviour)**: while support blocks a card, its owner can no longer save it or change its media (`409 card_disabled_by_support`), the dashboard shows it read-only; events stay editable and leads exportable (LNK-036) — handoff §6.3 "ni modifiable ni réactivable"; ADM-009's purpose is to stop an abusive card, which an owner could otherwise rewrite while blocked — cost if wrong: one guard on three routes.
- Ruling R-S25: when a slug is taken or reserved, the dashboard proposes the first three available of `<slug>-2`, `<slug>-3`… (LNK-035), not the mockup's "-photo"/"-clermont" — at creation only the names are known; LNK-019's sequence already exists and skips blocked slugs — cost if wrong: a smarter suggestion generator.
- Ruling R-S26 **(changes implemented behaviour)**: leaving the card editor or the event editor with unsaved changes through a dashboard link opens an `AlertDialog` with "Rester", "Quitter sans enregistrer" and "Enregistrer et quitter" (EDI-028), replacing the `window.confirm` of plan 2 (card editor) and plan 4 (event editor, EDI-021); tab close and reload keep the browser's prompt — handoff §6.4; a third choice saves a round trip; browsers forbid custom `beforeunload` dialogs — cost if wrong: one component.
- Ruling R-S27: the editor's inline avatar zoom slider ("Fais glisser la photo pour la centrer") is not built; "Recadrer" opens the avatar dialog (EDI-035) — with server-side crops each inline nudge would create a media and its files — cost if wrong: an inline control calling the same re-frame.
- Ruling R-S28: the "Contacts" navigation entry is a page that picks a card (first by default) and a scope (whole card or an event) and renders plan 4's lead list, detail and export components (EDI-031); plan 4's per-event and whole-card pages stay — handoff §6.7 draws one page with filters; plan 4 built the views per scope; reusing them keeps one implementation — cost if wrong: a cross-card list later.
- Ruling R-S29: phase B adds to the API `CardView.event_counts {running, upcoming, past}`, `CardView.lead_count`, `MeView.max_simultaneous_events` and `MeView.totals {cards, events, leads}` (EDI-023, EDI-024, EDI-032, ACC-027) — the card list summary, the deletion dialogs and the limit message need them, and the web cannot know the instance's limit (EVT-019) — cost if wrong: four fields.
- Ruling R-S30: coordination with plan 4 — phase A starts now without touching dashboard screens; phase B starts after plan 4's merge; plan 6 numbers rules after plan 4's (ACC-025+, ADM-021+, LNK-034+, EDI-022+, LEA-033+) and never cites a plan-4 rule (absent from `main`, `spec-lint` would fail); the wording change plan 6 needs on plan 4's ACC-019 ("reached from the header" → "from the dashboard navigation (EDI-022)") is made in Task B1; migrations 0007 and 0008 follow plan 4's 0006 — brief — cost if wrong: merge-time conflicts listed under "Points for the merge".
- Ruling R-S31: the `datetime` field of the e2e data is added to "Démonstration en boutique" (no lead, optional field), and e2e tests that need another theme set it through the API instead of the seed — plan 4's e2e tests read the Mariage export header exactly and count leads; the seed's card list is a likely merge conflict — cost if wrong: none.
- Ruling R-S32: the default poster time is 0 when an upload sends none (MED-028); the current editor sends 0.1 s, the time `capturePoster` uses, until the video dialog (EDI-034) sends the playhead — keeps the stored framing true to the captured frame — cost if wrong: none.
- Ruling R-S33: French typography (’, non-breaking spaces before `: ; ? !` and inside « ») is applied to every text plan 6 adds or touches, screen by screen, and a final sweep (Task B23) converts the rest with a test that scans `fr.json` — a sweep in phase A would break plan 4's e2e text assertions before its merge — cost if wrong: mixed typography until B23.
- Ruling R-S34: "Vos données personnelles" under the form links to the instance's privacy policy (ADM-021) — the mockup draws the link without a target; the owner-controller's own text is the consent text (FRM-026) — cost if wrong: a link to a per-card page later.
- Ruling R-S35: the form's band always reads "Événement en cours" while the form is open, including the 15-minute grace after the end (EVT-026) — one label for one screen; the grace period exists for prospects already filling the form — cost if wrong: one label.
- Ruling R-S36: on the public page and the form, the `--c-*` variables are set on the `.cc-page` wrapper (the area painted with the card's background), in the preview and thumbnails on the `.cc` card itself; never on `html` or `body` (TPL-026, reworded) — the desktop stage background (PUB-037) needs the card's colours outside the card — cost if wrong: none.
- Ruling R-S37 (pre-flight P6): a source's file name is `source-<token>.webp`, `<token>` being the 32 hexadecimal characters of a random UUID v4 drawn for each new media (upload, re-frame, duplication), stored in `media.source.name`; MED-031 reworded accordingly — in S3 mode (production) `MediaService::dashboard_url` returns the plain bucket URL and a fixed `source.webp` next to the public variants could be derived from any public URL, exposing the uncropped image; an unguessable name gives S3 the same protection as MED-024's unguessable bucket URLs, without presigned URLs; local mode keeps the signature check — cost if wrong: anyone holding the owner's dashboard address of a source can read it until the media is replaced (same exposure class as MED-024); presigned URLs on a private prefix would need an S3-specific code path.

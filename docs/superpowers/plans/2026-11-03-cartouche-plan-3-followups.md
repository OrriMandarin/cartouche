# Plan 3 — Suivis reportés

Décisions prises en écrivant la spec et le plan 3 (sans intervention du porteur du projet : chaque point qu'il aurait fallu lui signaler a été tranché et écrit en règle), puis décisions prises pendant l'exécution et constats mineurs relevés par les relectures, non corrigés. À trier par le `planner` lors des plans suivants.

## Décisions prises (rulings)

- Ruling R-S1: API shape — owner `GET|POST /api/cards/{id}/events`, `GET|PUT|DELETE /api/events/{id}`, `POST /api/events/{id}/end`, `GET /api/events/{id}/leads`, `PUT /api/leads/{id}/spam`, `DELETE /api/leads/{id}`; public `GET /api/public/cards/{slug}/events/{event_id}`, `POST …/unlock`, `POST …/leads`; new codes too_many_simultaneous_events/event_not_running/event_closed/form_changed/device_limit_reached 409, invalid_access_code 403, rate_limited 429 — short owner paths by event id (owner filter through the card join), public paths under the slug so the card's served state and theme are resolved once — cost if wrong: route renames + regenerated client.
- Ruling R-S2: an event with an access code returns only `{id, title}` until a correct code is posted to `/unlock`; the code is resent and rechecked at submission (EVT-027, FRM-041) — design 5.3 "un écran demande le code avant le formulaire", and the questions are not shown to people who are not at the stand; the code itself never leaves the server either way (EVT-012) — cost if wrong: one extra round trip; returning the form with the GET is a one-route simplification.
- Ruling R-S3: the simultaneous-event limit is made race-free by locking the card row (`cards::lock_for_owner`, `for update`) before reading the card's other events, in create, update (via `lock_card_of_event`, card locked first) — same pattern as plan 2's card saves; a serializable transaction would need retry handling — cost if wrong: creations on one card are serialized (negligible).
- Ruling R-S4: "le fuseau de l'utilisateur" = the browser's time zone, Europe/Paris when the browser gives none, zone name shown next to date inputs; no stored preference in v1; API is UTC RFC 3339 only; DST gap moves forward one hour, ambiguous time takes the first occurrence; Playwright pins `timezoneId: Europe/Paris`, `locale: fr-FR` (EVT-022, EVT-023) — the design names no preference screen, and a fixed Paris zone would contradict "fuseau de l'utilisateur" — cost if wrong: a user setting later, the conversion functions keep a `zone` parameter.
- Ruling R-S5: the form can be read, unlocked and submitted in the same window as EVT-008 (start → end + 15 min), while public buttons show only running events (EVT-026, PUB-029) — a prospect reloading the page during the grace period must not be locked out; one domain function (`accepts_submissions`) for all three — cost if wrong: a late visitor following an old link can still fill a form for 15 minutes.
- Ruling R-S6: device id = browser-generated UUID kept in cookie `cartouche_device` (path /, 400 days, SameSite=Lax) and localStorage, sent in the body as `device_id`, stored raw; counted per event including spam-marked leads, deleted leads excluded; concurrency via `pg_advisory_xact_lock` on (event, device) (EVT-028, EVT-029) — a random id is not personal data; spam-marking must not hand a bot a new slot; the advisory lock avoids serializing all submissions of an event — cost if wrong: hash the id before storing (one column).
- Ruling R-S7: IP limits = 120 submissions / IP / sliding 10 min (all outcomes counted), 30 failed codes / IP / 10 min (correct codes not counted); client IP = n-th entry from the right of X-Forwarded-For with `TRUSTED_PROXY_HOPS` (default 1), IPv6 grouped by /64; in-memory limiter behind the `RateLimiter` trait (single API instance in v1) (ABU-006 to ABU-008) — design §13 leaves values to the builder; 120/10 min lets a whole stand share one Wi-Fi; production has exactly one proxy (Caddy) in front of `/api`, dev/e2e have the Next rewrite — cost if wrong: two constants and one env default; a shared store if the API ever runs on several instances.
- Ruling R-S8: honeypot = text field named `fax`, positioned off-screen (not display:none), untabbable, aria-hidden, autocomplete off; a filled honeypot gets the same 204 as an accepted submission, nothing is stored, the device slot is not used; the IP limit still counts it (checked first) (ABU-005) — "ignoré silencieusement" read as indistinguishable from success — cost if wrong: field name only.
- Ruling R-S9: lead storage = typed columns for the standard answers (first/last name, birth date, email, phone E.164, street, postal code, city, country) + `custom_answers jsonb` with one `{field_id, label, kind, value}` snapshot per custom field present at submission (null when unanswered), `consent_at`, `consent_text`, `device_id`, `spam_at`; no IP, no user agent (FRM-038) — FRM-022/FRM-023 need snapshots; typed columns serve plan 4's search; no IP = minimal personal data — cost if wrong: one migration for plan 4 if it wants other columns.
- Ruling R-S10: `form_version` (FNV-1a 64 over the serialized public form: title, description, fields, resolved consent text) is returned with the form and must come back with the submission, else `409 form_changed`; the client reloads the form, keeps answers by field id and unchecks consent (FRM-030) — guarantees the stored consent text is the one the prospect saw (FRM-008), including after a card email change — cost if wrong: drop the check (one step of the submit handler).
- Ruling R-S11: default consent text written verbatim in FRM-026/FRM-027 and implemented in `cartouche-domain/consent.rs`, not in `fr.json` — the server must record the exact text accepted, so it must compose it; an explicit exception to "aucun texte d'interface en dur", recorded in CLAUDE.md by Task 18; a card always has a first or last name (PUB-018), so only the missing-email case needs a variant — cost if wrong: moving one template string if the text ever becomes translatable.
- Ruling R-S12: limit values (EVT-016, EVT-030, FRM-028, FRM-031 to FRM-036): title 120, description 2 000, code 32, device limit 1–100, ≤ 30 custom fields, label 100, help 300, 2–20 options of 100, consent 3 000, answers 100/254/200/20/500/5 000, dates 1900–2100, at least one field — design §13 leaves them to the builder; chosen in line with plan 2's content limits — cost if wrong: constants in the domain plus their tests.
- Ruling R-S13: deleting an event deletes its leads (cascade), after a confirmation that shows their count (EVT-024) — orphan leads would vanish from the per-event view (LEA-001) and keeping data without a purpose is against the RGPD spirit of FRM-010 — cost if wrong: `on delete set null` + a "deleted event" label in plan 4.
- Ruling R-S14: events of a disabled card (owner or support) stay listed and editable in the dashboard; publicly the form page shows the neutral page and the API answers `410 card_inactive`, like the vCard (EVT-025, FRM-024) — LNK-008 keeps the data visible; editing has no public effect while the card is unserved; LNK-026 already names 410 for the vCard — cost if wrong: refuse edits with `409 card_disabled_by_support` (one guard).
- Ruling R-S15: plan 3's lead surface = one page per event listing its leads (date, name, email, phone, Spam label) with spam toggle and delete (EDI-020); plan 4 adds search, detail view, card-wide view, exports and support access on top of the same routes — ABU-003/ABU-004 are plan 3 by status line, LEA-001 to LEA-012 stay plan 4 — cost if wrong: plan 4 restyles the page.
- Ruling R-S16: prospect-facing texts use "vous", dashboard texts keep "tu" (FRM-025) — the prospect is not a Cartouche user and speaks to the card owner's business — cost if wrong: wording in `eventForm.*` only.
- Ruling R-S17: the form, code screen and confirmation are one shared component rendered with the card theme; a template renders only the button towards `urls.eventForm(id)` (TPL-020); the template contract is unchanged and R-T15's `/c/<slug>/e/<id>` is kept — TPL-003 guarantees form behaviour whatever the template, which a shared component makes true by construction — cost if wrong: a template-level override hook later.
- Ruling R-S18: see the section below — local mode stops serving `/media/cards/{card_id}/…` of an unserved card (404, checked per request), with HMAC-signed dashboard/support URLs (≥ 24 h, random key at startup, `Cache-Control: private, max-age=86400`); S3 mode keeps files at their unguessable bucket URL, written as MED-024 — cost if wrong: drop the signature path (the dashboard of a disabled card would lose its images) or add a private bucket in a later plan.
- Ruling R-S19: seed scenarios receive "now" (`fn(&PgPool, DateTime<Utc>)`: the API clock through `/api/test/seed`, system time through `cartouche-seed`); the `events` scenario places its events around it, and e2e freezes the clock at `EVENTS_NOW = 2027-03-15T10:00:00Z` before seeding and before signing any token — deterministic e2e and a useful local dataset with one scenario — cost if wrong: fixed dates plus a documented clock step for local use.
- Ruling R-S20: the three public event routes accept an old slug or capitals without redirecting (the card behind it is served); the web page `/c/<old>/e/<id>` does redirect with 308 + no-store (FRM-024) — a submission must not fail because the owner renamed the slug mid-fill, while the visible address still converges to the current slug — cost if wrong: 308 on the API GET too.
- Ruling R-S21: an event's phase (`upcoming`/`running`/`past`) is computed by the server with `state.clock` and sent as `EventView.phase`; the dashboard groups by it, never by the browser clock (EVT-020) — otherwise the e2e test clock would be ignored and phases would disagree with the public page — cost if wrong: none.
- Ruling R-S22: "Terminer maintenant" is refused with `409 event_not_running` on an upcoming or past event; the 15-minute grace applies after it (EVT-021) — ending an upcoming event would create an end before its start (EVT-017) — cost if wrong: allow it on upcoming events by deleting instead.
- Ruling R-S23: plan-2 follow-ups without open questions — `loadVideo` gives up after 15 s (MED-021), MP4 brand allow/deny lists for `ftyp` (MED-022), every public 308 carries `Cache-Control: no-store` (LNK-030) — written as rules so the tests can cite them — cost if wrong: constants.
- Ruling R-S24: a `number` answer is accepted as a JSON number or a string with a dot or a comma, and stored as a JSON number (FRM-036) — French keyboards type a comma; accepting both server-side keeps a direct API caller and the browser consistent — cost if wrong: one parser.
- Ruling R-S25: the device-limit bounds (1–100) became their own rule EVT-030, found missing while writing EVT-016 — EVT-014 says "réglable" without bounds — cost if wrong: one constant.

## Point ouvert du plan 2 tranché

**Les fichiers `/media/*` d'une carte non servie ne sont plus servis en mode disque local ; ils restent lisibles en mode S3 (limite connue).** Règles MED-023 et MED-024, tâche 2 du plan 3.

- En mode local, l'API vérifie à chaque requête de `/media/cards/<carte>/…` que la carte est servie (ni désactivée par son propriétaire, ni bloquée par le support, propriétaire `approved`) et répond 404 sinon. La proposition du contrôleur est adoptée, avec un ajout : sans lui, l'éditeur du propriétaire (LNK-008 : « les données restent visibles dans le tableau de bord ») et l'aperçu du support (ADM-013 : « même désactivée, son contenu s'affiche ») d'une carte désactivée perdraient leurs images. Les adresses de médias des vues du tableau de bord et du support portent donc une signature HMAC (clé aléatoire tirée au démarrage de l'API, aucune variable d'environnement), valable au moins 24 heures et stable pendant une heure, qui les rend lisibles même quand la carte n'est pas servie ; ces réponses sont servies en `Cache-Control: private, max-age=86400` au lieu de l'en-tête `immutable` de MED-016.
- En mode S3, les fichiers restent à leur adresse du bucket, qui n'est pas devinable : les couper demanderait de déplacer les fichiers ou un bucket privé avec adresses signées, hors de la v1. Ils disparaissent quand le média est remplacé ou retiré (MED-018) ou quand la carte est supprimée (MED-019).
- Dans les deux modes, les copies déjà en cache chez les visiteurs (MED-016, un an) ne sont pas rappelées.

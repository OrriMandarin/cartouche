# Plan 7 — Follow-ups

Decisions taken while writing the plan 7 spec and plan (media on S3, server-side video, public-page loaders, dev build), then decisions taken during execution and minor findings raised by the reviews and not fixed. The owner decided: S3 everywhere (Garage in compose, local mode kept selectable), media on their own origin with exact stored headers and a sandboxing CSP in local mode, ffmpeg behind a trait with header videos transcoded server-side (crop and loop at encode, poster extracted by the server, original kept privately, bounded CPU and time), loaders for the header image, header video and avatar, and `opt-level = 3` for dependencies in dev with a measurement. Every other point was decided here, written as a numbered rule and recorded below. To be triaged by the `planner` in later plans.

Each ruling line: decision — reason — cost if wrong. Rulings marked **(changes implemented behaviour)** modify something plans 2 to 6 already shipped or specified.

## Rulings taken (spec/plan phase)

- Ruling R-S1 **(changes implemented behaviour)**: a header video's served file is transcoded by the server with its crop and loop applied (MED-004, MED-032, MED-034, PUB-004, PUB-005): H.264 High, `yuv420p`, no sound, ≤ 30 fps (`-fpsmax 30`), CRF 26, `+faststart`, duration = the loop; preset `medium` instead of HANDOFF §7's `slow`; the public page plays the file with `loop` and no CSS crop. This replaces plan 6's R-S1 (CSS crop, `timeupdate` loop, file served as uploaded) — owner decision for the transcode; `medium` because `slow` costs roughly twice the CPU for a few percent of size on a small VPS — cost if wrong: a slightly bigger file (switch the preset), or more CPU per upload.
- Ruling R-S2: the served file's width is the crop's width in pixels of the displayed frame, capped at 1,280 and rounded down to a multiple of 8, its height three quarters of it (exact 4:3, even sides, never enlarged); a crop narrower than 16 px is refused `invalid_crop` (MED-035) — a multiple of 8 gives an exact 4:3 with even sides, which `yuv420p` requires; HANDOFF §7 gives 1,280 × 960 — cost if wrong: up to 7 px of width lost on small crops.
- Ruling R-S3: a video's source becomes its edit copy, `source-<32 hex>.mp4` in the public bucket: whole frame and whole video, longer side ≤ 960 px (even sides, never enlarged), CRF 30, preset `veryfast`, no sound, `+faststart`; it is owner-only exactly like an image source (MED-031: signed in local mode, unguessable name in S3 mode) and drives the crop dialog (EDI-034, MED-037); `SourceFile` keeps name/width/height, so no migration — the dialog needs a playable, seekable, CORS-readable video of the whole frame; the original cannot be served (MED-036), the served file is already cropped — cost if wrong: an extra ~1–3 MB per video in the bucket.
- Ruling R-S4: the private original is the uploaded bytes as they are (MED-036), in a private store; it is the input of every re-frame (no generational loss), copied on re-frame and on card duplication, deleted with the media and the card — owner decision to keep the original — cost if wrong: the original keeps the uploader's metadata (location included) in private storage; see the open point on remuxing it without metadata.
- Ruling R-S5: the served file and the edit copy keep only the first video stream and none of the metadata (`-map 0:v:0`, `-an`, `-map_metadata -1`, MED-038) — the same privacy line as MED-007 for photos — cost if wrong: none.
- Ruling R-S6 **(changes implemented behaviour)**: the browser no longer captures or sends a poster; the server extracts the full displayed frame at the poster time (the last frame at or past the end) and the image pipeline cuts the placeholder variants from it (MED-003, MED-029); a `poster` form field is refused with `400 invalid_request` on upload and re-frame; `poster_required` disappears (MED-013); `capturePoster` and `canvas.ts` are deleted — one source of truth for the frame, no CORS needed to capture it — cost if wrong: an old client that still sends `poster` gets a 400 (the web is deployed with the API).
- Ruling R-S7 **(changes implemented behaviour)**: the video size limit goes from 25 to 50 MB (MED-002); upload body limit 36 → 52 MiB; Next `proxyClientMaxBodySize` 40mb → 56mb; Next `experimental.proxyTimeout` 30 s → 180 s (development and the web image) — a 30 s 1080p phone clip in H.264 is about 60 MB and 25 MB held only ~12 s, now that the server re-encodes, a heavier input costs no visitor bandwidth; the proxy must outwait the 120 s processing deadline plus the transfer — cost if wrong: more memory per upload in flight (the body is buffered) and a longer wait before a refusal.
- Ruling R-S8: one video job at a time (its own semaphore, separate from the two image permits), one 120 s deadline from the moment the request asks for the permit (wait and run) → `503 video_processing_timeout`, the ffmpeg process killed and reaped before the permit is released; ffprobe/ffmpeg failure on the file → `400` field `file` code `video_unreadable`; a displayed side > 4,096 px → `400` field `file` code `video_too_large` (MED-039) — bounded CPU and time on a small VPS; 4,096 admits 4K UHD — cost if wrong: two owners uploading at once wait for each other; a second-in-line upload of a long clip may time out (T19 measures).
- Ruling R-S9: only H.264, HEVC, VP9 and AV1 video streams are decoded; anything else is refused with `415 unsupported_media_type` (MED-040) — what phones and browsers produce (VP9 is the e2e fixtures' codec); every other ffmpeg decoder stays out of reach of hostile files — cost if wrong: an exotic but legitimate file (MPEG-4 Part 2, ProRes) is refused.
- Ruling R-S10: the duration stays the server's own `mvhd` read (MED-013, unchanged); ffmpeg reads at most that duration (`-t`) — the 30 s check stays before any process is started — cost if wrong: none.
- Ruling R-S11: a video's crop is checked and converted on its displayed frame (rotation applied, from ffprobe's side data) (MED-026); the edit copy's even rounding stays within the 1 % shape tolerance — phone portrait clips are stored landscape with a rotation — cost if wrong: none.
- Ruling R-S12 **(changes implemented behaviour)**: a video uploaded before plan 7 (its source is a `.webp`, or it has none) is shown as before minus its crop and loop: its file as uploaded covers the header, centred, and loops over its whole length; its placeholder stays the one cut along its crop (MED-033); it cannot be re-framed (`409 media_not_reframable`) and its view has no `source`, so the editor offers no "Recadrer" (MED-030) — no production data exists yet; re-encoding old videos would need their crop applied to a file that is already public — cost if wrong: a test card with a plan-6 video shows its uncropped frame until the video is replaced.
- Ruling R-S13: ffmpeg sits behind a `VideoProcessor` trait (`probe`, `render`); the route tests use a stub in `test_support`; real-ffmpeg tests in `tests/it/video_ffmpeg.rs` run on committed fixtures and are required, never skipped (CI installs ffmpeg); `FFMPEG_PATH`/`FFPROBE_PATH` (defaults `ffmpeg`/`ffprobe`); the API checks `-version` and the `libx264` encoder at startup and refuses to start otherwise (MED-041) — CLAUDE.md requires every external dependency behind an interface; a missing ffmpeg must fail at deploy time, not on the first upload — cost if wrong: `make api` and `make test` need ffmpeg on every developer machine.
- Ruling R-S14: private originals go to a second bucket, `MEDIA_S3_PRIVATE_BUCKET`, on the same endpoint, region and keys; in local mode, under `private/` of the media directory (`PrefixStore`), which `/media/*` cannot reach (MED-044) — Garage, like many providers, exposes a whole bucket or nothing; two buckets port to OVH as two containers — cost if wrong: one more bucket to provision; a provider with per-prefix policies could use one.
- Ruling R-S15 **(changes implemented behaviour)**: `MEDIA_STORAGE` absent now means `s3` (MED-009); `local` must be set explicitly; `scripts/check-prod-guard.sh` and every config test fixture set `MEDIA_STORAGE=local` — a production deploy that forgets the variable must fail to start, not write media to the container's disk — cost if wrong: anyone running the API by hand without the Makefile must set two more variables.
- Ruling R-S16: the API refuses to start in S3 mode when `MEDIA_PUBLIC_BASE_URL` has the origin of `PUBLIC_BASE_URL` (MED-042) — the isolation the owner asked for is only real on another origin — cost if wrong: a deployment that wanted media under the app's domain path must use a subdomain.
- Ruling R-S17 **(changes implemented behaviour)**: every public S3 object is stored with `Content-Disposition: inline` besides its exact type and the immutable cache policy (MED-043); `X-Content-Type-Options: nosniff` cannot be stored as S3 object metadata (S3 and Garage only keep the standard headers), so it is left to plan 5 (a proxy or CDN in front of the bucket) — cost if wrong: a browser may sniff a file served by the bucket, which only ever holds files the server produced itself.
- Ruling R-S18 **(changes implemented behaviour)**: in local mode every `/media/*` response adds `Content-Security-Policy: sandbox; default-src 'none'` and `Content-Disposition: inline` to the existing `nosniff` (MED-046) — local mode serves media from the app's origin, so a file opened on its own must not run anything there — cost if wrong: none for images and video elements; a media URL opened directly shows the file without scripts.
- Ruling R-S19: MED-023 and MED-024 stay as they are: in S3 mode the files of a card that is not served stay readable at their unguessable bucket addresses and the dashboard gets plain bucket addresses (no presigned URLs) — owner decision to keep plan 6's line; plan 5 may put a `forward_auth` in front of the bucket — cost if wrong: a disabled card's media stay reachable by whoever kept their address.
- Ruling R-S20 **(changes implemented behaviour)**: the public bucket answers CORS `GET`/`HEAD` from the app origin only (MED-045), configured by the dev and test init scripts and documented for plan 5; plan 6's owner follow-up "S3 bucket CORS" (needed for the poster capture) is replaced by this need (the strip frames of the video dialog) — `captureFrames` draws the edit copy in a canvas with `crossOrigin="anonymous"` — cost if wrong: without it, the strip stays empty in S3 mode (the dialog still works).
- Ruling R-S21: loaders (PUB-006, PUB-039 to PUB-042): the header image and the profile photo show the theme's surface colour (`--c-surface`) under the sheen; the video keeps its blurred placeholder; on error the sheen and `aria-busy` go (video: placeholder kept, sharp; image and avatar: surface kept, the broken image hidden); a mount-time check of `img.complete`/`naturalWidth` and `video.readyState`/`error` catches loads finished before hydration; without JavaScript a `<noscript>` style removes the sheen and the blur (the server-rendered markup still says `aria-busy="true"`); under reduced motion the placeholder is sharp and no sheen moves — HANDOFF §4 and the two bugs found (lost early events, no `error` handling) — cost if wrong: none.
- Ruling R-S22: Garage `dxflrs/garage:v2.5.0` runs in `compose.dev.yml` and `compose.test.yml` in single-node mode with its default key and public bucket from environment variables, a config file in `docker/garage/garage.toml` and a one-shot, idempotent `garage-init` (`curlimages/curl` + `docker/garage/init.sh`: private bucket, key permissions, website access and the `localhost` alias on the public bucket, CORS); the key, secret, admin token and RPC secret are fixed and marked dev-only; `make dev-db` starts Postgres, Garage and the init (no new target); dev ports `DEV_S3_PORT` (3900), `DEV_S3_WEB_PORT` (3902), `DEV_S3_ADMIN_PORT` (3903), one set per worktree; test ports fixed at 13900 and 13902 — the brief's verified behaviour (alias `localhost` makes the web endpoint serve the bucket on another port, i.e. another origin) — cost if wrong: a developer whose ports collide sets them in `.env`.
- Ruling R-S23: the end-to-end stack runs in S3 mode only; local mode keeps its coverage in the Rust integration tests (`/media/*`, signatures, cut-off) — e2e must test what production runs — cost if wrong: a web-side regression specific to local mode (same-origin media) is caught by no e2e.
- Ruling R-S24: if Playwright's bundled Chromium cannot decode H.264 (the fixtures README says so), the desktop project runs Google Chrome (`channel: "chrome"`) and CI installs it; WebKit (mobile project) is expected to decode H.264 (AVFoundation on macOS, GStreamer libav on Linux); measured in T15 before any test relies on it — the served file is H.264 by design (MED-034) — cost if wrong: Chrome must be installed on every developer machine that runs `make e2e`.
- Ruling R-S25: fixtures are committed: backend clips under `backend/server/tests/fixtures/video/` (≤ 300 KB each: 1080p60 with sound and a location tag, a rotated portrait clip, a small VP9 24 fps clip, an audio-only file, a truncated file) and e2e files `photo-24mpx.jpg` (~5–6 MB) and `header-1080p.mp4`, each with its ffmpeg command in a README — deterministic tests that do not depend on the encoder version of the machine — cost if wrong: about 7 MB more in the repository.
- Ruling R-S26: the S3 integration tests (`tests/it/media_s3.rs`) run against the developer's own Garage, configured from the `MEDIA_S3_*` variables the Makefile exports, under fresh card ids; they are required, so `make test` needs `make dev-db` (and ffmpeg) — the headers, Range, CORS and private-bucket checks only mean something against a real S3 server — cost if wrong: `make test` fails with a clear message when Garage is down.
- Ruling R-S27: the editor's messages for the new codes (EDI-037): « Cette vidéo ne peut pas être lue : essaie un autre fichier MP4 », « Cette vidéo est trop grande (4 096 pixels de côté au plus) », « La préparation de la vidéo a pris trop de temps : réessaie dans un instant », and the too-heavy message now says 50 Mo — written in the style of the existing messages — cost if wrong: wording only.
- Ruling R-S28: a 4:3 video chosen without the dialog still sends `poster_time` 0.1 s (`POSTER_SECONDS`, plan 6's R-S32), now as the time the server extracts — the first frame of a phone clip is often black — cost if wrong: none.
- Ruling R-S29: duplicating a card copies each video's private original to the copy (MED-036, EDI-014) — the copy must stay re-framable — cost if wrong: none.
- Ruling R-S30: the video dialog's poster box only sets the poster time; `VideoFraming.newPoster` disappears; a re-frame always sends the poster time (the kept one when the box is unchecked) (EDI-034) — the server extracts the frame either way — cost if wrong: none.
- Ruling R-S31: `MediaView.duration_seconds` stays the original's duration, so that the dialog's loop handles span the whole video; the served file lasts the loop (MED-034); the editor's badge « Vidéo · {seconds} s » therefore shows the original's length — the stored loop is relative to the original — cost if wrong: the badge shows the full length rather than the loop's (see open points).

## Points for plan 5 (production)

- **Buckets on OVH Object Storage**: two containers in the same region, one public-read (`MEDIA_S3_BUCKET`) and one private (`MEDIA_S3_PRIVATE_BUCKET`, no public access, no static website); `MEDIA_S3_ENDPOINT` (`https://s3.<region>.io.cloud.ovh.net`) and `MEDIA_S3_REGION` (e.g. `gra`) to confirm against OVH's documentation; versioning and lifecycle rules off (files never change, MED-016); a backup policy for the private bucket (originals are the only re-frame input).
- **Public URL and custom domain**: `MEDIA_PUBLIC_BASE_URL` on its own origin (e.g. `https://media.<domain>`), HTTPS, never the app's origin (the API refuses it, MED-042); check that the provider serves the stored `Content-Type`, `Cache-Control` and `Content-Disposition` and honours `Range` (MED-017).
- **CORS** on the public bucket: `GET` and `HEAD` from `PUBLIC_BASE_URL` only, exposing `Content-Length`, `Content-Range`, `Accept-Ranges` (MED-045); the dev init script (`docker/garage/init.sh`) holds the exact XML.
- **Keys**: one access key with read and write on both buckets for the API, nothing else; never the account's root key; rotation procedure.
- **Caddy**: request body ≥ 52 MiB and read/response timeouts ≥ 180 s on `POST /api/cards/*/media` and `/reframe` (MED-002, MED-039); the web container's Next proxy already allows 56 MB and 180 s.
- **`nosniff` cannot be stored in S3** (R-S17): if a proxy or CDN fronts the bucket, it adds `X-Content-Type-Options: nosniff` (and can add the sandbox CSP of MED-046).
- **Optional cut-off of unserved cards** (MED-024, R-S19): a Caddy `forward_auth` in front of the bucket asking the API whether `cards/<card>/…` is served, if the owner wants it.
- **CPU**: one transcode at a time (MED-039); measure a 30 s 1080p upload on the production VPS (T19 gives the dev-machine numbers); the API image grows with Debian's ffmpeg (~150–250 MB): a static ffmpeg build is an option if the size matters.
- **`MEDIA_STORAGE`**: leave it unset or `s3` in production (R-S15).

## Open points (not decided, for the owner or a later plan)

- **Metadata in the private original**: the original keeps the uploader's metadata, location included (R-S4). Storing it remuxed instead (`-map 0:v:0 -c copy -map_metadata -1`: no re-encode, no quality loss, no sound, no location) would satisfy MED-038's spirit for stored data too; it changes MED-036 ("the uploaded bytes").
- **QuickTime `.mov`**: iPhones record QuickTime files, which MED-022 refuses; now that every video is transcoded, accepting the `qt  ` brand would cost nothing more on the server. Not done (MED-022 unchanged).
- **HDR and 10-bit inputs** (HEVC HLG/PQ from recent phones) are converted to 8-bit `yuv420p` without tone mapping: colours may look washed out. A `zscale`/`tonemap` step would need an ffmpeg built with `zimg`.
- **A message while the server prepares the video**: the field shows « Envoi en cours… » for the transfer and the transcode together (up to two minutes); a distinct « Préparation de la vidéo… » would need upload progress events.
- **The badge « Vidéo · {seconds} s »** shows the original's duration, not the loop's (R-S31).
- **Developing from a phone on the LAN** in S3 mode: the bucket's `http://localhost:<port>` address is not reachable from the phone (and Garage picks the bucket from the `Host` header); `MEDIA_STORAGE=local` is the documented workaround (T9, T18).
- **Videos uploaded before plan 7** keep their uncropped files (R-S12); a one-off script could re-encode them from their stored file and framing if production data ever exists before this ships.

## Measurements

Measured on 2026-11-07 (T19): Apple M1, 16 GB, macOS, ffmpeg 8.1.2. The API was a `make api` debug build with `test-support`, in S3 mode (the worktree's Garage), and the site ran under `next dev`. Each file was uploaded three times as Alice's header with `curl` through the web origin (the Next proxy, `POST /api/cards/<id>/media`). The table gives the median wall time of the request, and every run answered 201.

| File | Dependencies at `opt-level = 3` (the branch) | Without the `[profile.dev.package."*"]` block | Gain |
|---|---|---|---|
| `photo-24mpx.jpg` (6,000 × 4,000, 5.9 MB) | 4.0 s (3.7 / 4.0 / 4.3) | 78.3 s (78.3 / 80.1 / 73.1) | × 20 |
| `landscape-1080p60-audio-gps.mp4` (4 s, 1080p60, sound) | 2.0 s (2.1 / 1.8 / 2.0) | 8.0 s (7.7 / 8.0 / 10.7) | × 4 |
| 30 s 1080p30 H.264 + AAC clip, 41 MB, generated locally | 18.5 s (18.5 / 19.2 / 18.1) | 30.5 s (34.3 / 30.5 / 30.4) | × 1.6 |

- The 30 s clip stays well under the 120 s deadline (MED-041) in both builds. Most of its time is the ffmpeg encode, which the Rust profile does not change. The remaining gap is the Rust side: decoding the extracted frame, and encoding the three WebP widths of the placeholder and the source.
- A clean `cargo build` of the API takes 8 min 36 s with the block. Switching the dependencies back to `opt-level = 0` takes 1 min 53 s. Day-to-day rebuilds touch only the workspace crates and are unchanged.
- The 30 s clip was generated with `ffmpeg -f lavfi -i "testsrc2=s=1920x1080:r=30:d=29.5,noise=alls=12:allf=t" -f lavfi -i "sine=frequency=440:duration=29.5" -c:v libx264 -preset veryfast -b:v 11M -maxrate 12M -bufsize 24M -pix_fmt yuv420p -c:a aac -b:a 128k -shortest phone-30s-1080p.mp4` (not committed).

## Rulings taken during execution

(Filled during execution: R-E for the tasks.)

- **R-E-T3 (ffmpeg 5.1)**: every invocation of the T3 adapter was run by hand in `debian:bookworm-slim` with its ffmpeg 5.1.9 (`-fpsmax`, `-sseof`, `-update 1`, `stream_side_data=rotation` in ffprobe, autorotate inside `-filter_complex`, `split`): all accepted; outputs H.264 High at the expected sizes (1280×960 and 960×540; rotated clip 1080×810 and 540×960, upright, no rotation side data), full-frame posters (1920×1080, 1080×1920). Measured there (probably emulated amd64): 25 s for the 4 s 1080p60 clip, 13 s for the 3 s rotated 1080p30 clip; on the Mac with ffmpeg 8.1.2 a whole probe + render + poster takes about 3 s.

- **R-E-T17 (browser decision, R-S24)**: Playwright 1.64.1's bundled Chromium and WebKit decode and play H.264 on macOS and on Linux (checked in `mcr.microsoft.com/playwright:v1.64.1-noble`: `canPlayType` "probably", `videoWidth` 640, `readyState` 4, playing). R-S24's Chrome fallback does not apply: no `channel: "chrome"`, CI keeps `playwright install --with-deps chromium webkit`. The probe ran on an arm64 container and again on `--platform linux/amd64`, the CI runners' architecture, with the same result. `compose.test.yml` brings `garage` and the one-shot `garage-init`, which `docker compose up -d --build --wait` accepts once exited, so the e2e job's stack step is unchanged; its failure dump (`docker compose logs`) includes Garage.

## Review findings deferred

- **T16, MED-038**: the e2e test checks that the sound track is dropped; the dropped metadata (location, dates, device) is covered by the Rust tests of the ffmpeg adapter (`tests/it/video_ffmpeg.rs`, with the GPS-tagged fixture), not end to end.
- **T16, MED-026 EDI-034**: the "Apply right away" regression test checks a 1,280 × 960 result, which any 4:3 crop gives; it guards the race (a non-4:3 crop is refused) but not the position of the default centred crop, which `CropDialogLayout.test.tsx` and `framing.ts` tests cover.

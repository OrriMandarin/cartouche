# Plan 4 — Follow-ups

Decisions taken while writing the plan 4 spec and plan (without the project owner: every point that would have been reported to them was decided and written as a numbered rule), then decisions taken during execution and minor findings raised by the reviews and not fixed. To be triaged by the `planner` in later plans.

Each ruling line: decision — reason — cost if wrong. Rulings marked **(changes implemented behaviour)** modify something plans 1 to 3 already shipped.

## Rulings taken (spec/plan phase)

- Ruling R-S1: API shape — owner `GET /api/cards/{id}/leads` (whole card), `GET /api/events/{id}/leads/export` and `GET /api/cards/{id}/leads/export` (query `format=csv|xlsx|json` required, `include_spam` default `false`, `tz` optional); support `GET /api/admin/cards/{id}/events`, `GET /api/admin/events/{id}/leads`, `GET /api/admin/cards/{id}/leads`; account `DELETE /api/me` → 204; new code `cannot_delete_admin` 403; `LeadView` gains `event_title` — same short owner paths as plan 3 (R-S1 of plan 3), owner filter through the card join; exports are plain GETs so one authenticated fetch downloads them — cost if wrong: route renames and a regenerated client.
- Ruling R-S2: search is done in the browser on the loaded list (`lib/events/lead-search.ts`), words ANDed, case and accents ignored, fields first name, last name, email, city, phone (digits, leading zeros dropped) and text/long text/single choice answers; no pagination (LEA-014 to LEA-016) — plan 3 already loads the whole list, filtering is instant, the same function serves the owner and support views, a business card's fairs give hundreds of leads, not millions — cost if wrong: a server-side `q` parameter and paging if a card ever holds tens of thousands of leads.
- Ruling R-S3: the detail view is a dialog over the list, built from the list's data; no `GET /api/leads/{id}` route; it records no audit entry (ADM-019) — `LeadView` already carries every answer and the consent text; one audit row per list request is what an administrator really obtained — cost if wrong: no deep link to one lead.
- Ruling R-S4: exports are generated on the server, in `cartouche-domain::export`, with the `csv` and `rust_xlsxwriter` crates named by the design (§7.2) plus `chrono-tz`; tests read XLSX files back with `calamine` (dev-dependency) — the design puts export generation in the domain — cost if wrong: three dependencies.
- Ruling R-S5: the French column headers, "Oui"/"Non" and the sheet name live in `cartouche-domain/src/export/labels.rs`: a second documented exception to "no hard-coded interface text", recorded in `CLAUDE.md` by Task 15; JSON keys are English and stable (LEA-030) — the files are opened by French users in Excel and Notion and are built by the server, which has no access to `fr.json`; one table keeps an English locale addable — cost if wrong: move one table or add a `lang` parameter.
- Ruling R-S6: CSV and XLSX dates are in the browser's time zone, sent as `tz` (IANA name); an unknown zone falls back to Europe/Paris; the two time headers name the zone; JSON keeps UTC RFC 3339 (LEA-026) — plan 3's R-S4 keeps the API in UTC, but a file read by people must show local times, and summer time makes any fixed offset wrong — cost if wrong: one query parameter.
- Ruling R-S7: the CSV is RFC 4180 with commas, CRLF and a BOM, numbers with a point, no `sep=` line; the export dialog points Excel users to XLSX (LEA-027) — Notion's import expects commas and a header first line, French Excel expects semicolons; XLSX serves Excel natively — cost if wrong: a semicolon variant.
- Ruling R-S8: CSV formula injection is neutralized with a leading apostrophe on text starting with `=`, `+`, `-`, `@`, tab or CR, phone and numbers excepted; XLSX texts are always text cells (LEA-028, LEA-029) — prospect input is untrusted and a CSV opened in Excel runs formulas; the validated phone and numbers must stay usable in Notion — cost if wrong: an apostrophe visible in Notion on a rare value.
- Ruling R-S9: column planning (LEA-023 to LEA-025): a standard column appears when an event of the export asks for it or a lead answered it (address columns together); custom columns per event by start, current fields then deleted ones; in a whole-card export, same label (case and accents ignored) and same type share one column across events, never within one event; duplicate headers get " (2)", " (3)"; a cell follows the type recorded with its answer — LEA-011 wants deleted fields; Notion needs unique headers; an owner expects one "Entreprise" column per card — cost if wrong: one domain function and its tests.
- Ruling R-S10: rows oldest first, the "Événement" column always present, exports not filtered by the search, disabled cards exportable (LEA-021, LEA-023) — chronological order suits a spreadsheet; LNK-008 says "exportables" — cost if wrong: a sort order.
- Ruling R-S11: file name `contacts-<slug>[-<event>]-<YYYY-MM-DD>.<ext>`, ASCII only (slugs are ASCII by LNK-018), `Content-Disposition: attachment`, `Cache-Control: no-store` (LEA-022, LEA-032) — no RFC 5987 encoding needed; no cache should keep prospects' data — cost if wrong: a file name format.
- Ruling R-S12: the browser downloads an export with `fetch` and the bearer token, then a blob, an object URL and an `<a download>` click, the name read from `Content-Disposition` (like `uploadMedia`) — the token is not a cookie, so a plain link cannot authenticate; signed one-shot URLs would put a credential in an address — cost if wrong: the whole file in memory (fine at these volumes).
- Ruling R-S13: support access to leads (ADM-016 to ADM-020): read-only routes, no export, spam or delete for administrators; viewing events is not audited; every lead list request is audited (`leads.viewed`, target `event` or `card`, metadata `owner_id`, `card_id`, `lead_count`) in the same transaction as the read, before the response, fail-closed; an administrator's own leads are audited too; audit entries hold no prospect data — design 5.8 "chaque consultation des contacts d'un autre utilisateur … il faut pouvoir le justifier" and ADM-012 "consulter seulement"; auditing own views avoids a special case — cost if wrong: an administrator needing a file asks the owner.
- Ruling R-S14: any account can delete itself whatever its status; a current administrator cannot (`403 cannot_delete_admin`), the operator removes them from `ADMIN_USER_IDS` first (ACC-021) — the right to erasure must not depend on approval; an administrator deleting themselves would be recreated approved on their next request (ACC-003) and would break the attribution of their audit entries while they are still an administrator — cost if wrong: one guard.
- Ruling R-S15: deletion runs in one transaction: lock the user row, block every slug of the user (hashes), strip slugs from the audit metadata, delete the user row (cascades to cards, slugs, media rows, events, leads), then delete each card's media prefix in storage, then commit; a storage error rolls everything back → `500 internal_error` (ACC-022) — "all data deleted" must not report success while photos remain; the reverse failure (files gone, rows kept) only affects an account its owner is deleting, and a retry completes it — cost if wrong: a transaction held open during storage calls, for a rare operation.
- Ruling R-S16: Cartouche never calls the identity provider (ACC-013): after a 204 the dashboard goes to `/account-deleted`, outside `AccountGate`, which calls `signOut()` and tells the user to delete their provider account there; a later sign-in creates a new empty account (ACC-001, ACC-002: `pending` in approval mode); no tombstone of the `sub` is kept (ACC-023) — a tombstone would be personal data kept after deletion (LNK-016) — cost if wrong: a deleted user can come back as a new user, which approval mode shows to administrators.
- Ruling R-S17: the confirmation dialog requires typing "SUPPRIMER" (case and surrounding spaces ignored) (ACC-020) — the action is irreversible and wide; typing the email is impossible because the email is optional — cost if wrong: one input.
- Ruling R-S18: blocked slugs: table `blocked_slugs (slug_hash bytea primary key)`, filled in SQL with `sha256(convert_to(slug, 'UTF8'))`, nothing else stored; a claim locks the `card_slugs` row (`for update`) first and checks `blocked_slugs` afterwards, in a new statement, so a concurrent deletion always wins; a blocked slug resolves like a deleted card (neutral page, 410) (LNK-031 to LNK-033) — the design says "empreinte (hash)"; the hash is unsalted on purpose: a slug was public, so confirming that a guessed slug was once used reveals nothing new, and a keyed hash would need a persistent secret whose loss would unblock every slug — cost if wrong: none for correctness; a keyed hash later needs a migration.
- Ruling R-S19: migration 0006 drops the foreign key of `audit_log.actor_user_id` (the value stays) and account deletion removes the `slug` key from the metadata of entries whose `metadata->>'owner_id'` is the deleted user; entries are kept (ACC-024) — accountability of administrator actions must survive an account deletion, but LNK-016 forbids keeping a slug tied to the person; without the change, deleting a former administrator fails on the foreign key — cost if wrong: dangling actor identifiers for former administrators.
- Ruling R-S20 **(changes implemented behaviour)**: ACC-004 is amended: deleting one's own account is, with `GET /api/me`, open to `pending`, `rejected` and `suspended` accounts, whose screens offer the action (ACC-019, ACC-021) — erasure for every account — cost if wrong: a suspended abuser can erase their data, which ACC-018 allows anyway.
- Ruling R-S21 **(changes implemented behaviour)**: the lead list no longer repeats the email of a nameless lead (LEA-017), and a successful spam toggle or deletion updates the list from the response instead of a full reload, so a failed reload can no longer leave a deleted row visible (LEA-020) — plan 3 Task 15 minors — cost if wrong: none.
- Ruling R-S22 **(changes implemented behaviour)**: marking a lead already marked as spam keeps its first `spam_at` (`coalesce`); the API still exposes only a boolean — plan 3 Task 10 minor — cost if wrong: none.
- Ruling R-S23 **(changes implemented behaviour)**: the event editor asks before leaving with unsaved changes, like the card editor (EDI-021) — plan 3's R-E5 follow-up; a long form is cheap to lose on a stray click and the card editor's mechanism is reused as is — cost if wrong: one small task.
- Ruling R-S24: the `events` seed scenario gives Jean-Michel's lead ("Salon de Paris 2026") an answer to a field deleted since ("Entreprise", text, "Hébert & Fils"); no new event or lead is added; `seed_lead` builds the consent text from the normalized title — e2e needs a deleted field in the detail view and in exports without changing the counts other tests read (plan 3 Task 11 minor) — cost if wrong: none.
- Ruling R-S25: the support event list reuses `EventView`, access code included — ADM-007 shows events as the owner sees them; the code is no prospect data — cost if wrong: an `AdminEventView` without the code.
- Ruling R-S26: the plan-3 deferred items not taken up stay in this file's "Deferred findings (carried over from plan 3)" with a one-line reason each — keep a single place to triage them next — cost if wrong: none.

## Deferred findings (plan 4 reviews)

Raised by the task reviews or the final review, not fixed, to be triaged by a later plan:

- Account deletion lists then deletes a card's media prefix: a media upload by the same user that lands in storage after the listing leaves an orphan file (LNK-016), only through the user's own concurrent action (`routes/account.rs`, `media/service.rs::delete_prefix`).
- In `next dev`, React StrictMode mounts the lead list twice, so one support view can write two `leads.viewed` audit rows; production builds write one (documented in the `dev-env` and `debug-failure` skills).
- Lead search does not fold the typographic apostrophe: "d'aubigne" typed with a straight apostrophe does not find "D’Aubigné" (LEA-015 only requires case and accents).
- Export headers: a generated " (2)" suffix is not checked against a literal "X (2)" label, so two headers could collide in a rare case (Notion wants unique headers) (`export/table.rs::suffix_duplicates`).
- Export headers: a deleted field's header and type come from the most recent exported snapshot even when its value is null; LEA-024 says "most recent answer" (`export/table.rs`).
- A modified click (ctrl/meta) on an internal link from a dirty editor still asks, although it opens a new tab (`lib/leave-guard.ts`).
- The real Clerk and OIDC sign-out return trips (R-E4) are covered only by mocked unit tests; e2e uses the test provider.
- The shared e2e stack (`cartouche-test`, fixed ports) breaks when two worktrees with different migration sets use it in turn ("migration N was previously applied but is missing"); `make e2e-down` before a run fixes it (seen at the final gate).

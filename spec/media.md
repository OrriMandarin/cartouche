# Media

> Status: implemented (plans 2, 3 and 6); amended by plan 7

## Header backgrounds and profile photo

- **MED-001** — A card has a single header background, which is an image or a video.
- **MED-002** — The header video is in MP4 format, limited to 30 s and 50 MB.
- **MED-003** — When a video is uploaded or re-framed, the server extracts from its uploaded file (MED-036) the whole frame at the poster time (MED-028), or the video's last frame when the poster time is at or past its end, and makes the placeholder image from it (see PUB-006 and MED-029). The browser sends no image with a video: an upload or a re-framing that carries one (a `poster` field) is rejected with `400 invalid_request`.
- **MED-021** — If the browser could not read a video chosen in the editor after 15 seconds, the upload is abandoned with a message, and the field becomes usable again.
- **MED-004** — Header videos are transcoded by the server (MED-034): the file uploaded is never served as it is.
- **MED-005** — A card has a single profile photo, square and shown in a circle. Its square is chosen in the editor (EDI-026) and cut by the server (MED-027).

## Image processing

- **MED-006** — Images are resized to several sizes and converted to WebP on the server.
- **MED-007** — The EXIF metadata of images, including the GPS location, is removed.
- **MED-008** — A file's type is checked from its actual content, not only from its extension.
- **MED-012** — Accepted images are JPEG, PNG or WebP, weigh at most 10 MB and have at most 40 million pixels; dimensions are checked before decoding the whole image. A rejected type gives `415 unsupported_media_type`, a file that is too heavy `413 payload_too_large`, an image that is too large `400` with the code `image_too_large`.
- **MED-022** — A video is recognized as MP4 only if the major brand of its `ftyp` box, or one of its compatible brands, is an MP4 brand (`isom`, `iso2` to `iso6`, `mp41`, `mp42`, `avc1`, `M4V `, `dash`), and its major brand is not that of another format (QuickTime `qt  `, 3GP `3gp*` and `3g2*`, audio `M4A ` and `M4B `, images `heic`, `heix`, `mif1`, `msf1`, `avif`). Otherwise it is rejected with `415 unsupported_media_type`.
- **MED-013** — A video's duration is read from the file by the server, without trusting the browser; beyond 30 s, the video is rejected with the code `video_too_long`.
- **MED-014** — A photo's EXIF orientation is applied before its metadata is removed: the photo displays the right way up.
- **MED-015** — Sizes produced, never enlarging the cropped area: for the profile photo, squares of 128, 256 and 512 pixels in WebP, plus 256 and 512 pixels in JPEG for the vCard and the link preview (see PUB-025 and PUB-028); for the header image and a video's placeholder image, 4:3 images 750, 1,125 and 1,440 pixels wide in WebP, whose height is the width × 3/4 rounded to the nearest pixel. Media uploaded before plan 6 keep the files produced then (640, 1,080 and 1,920 pixels wide, uncropped).

## Video processing

- **MED-034** — A header video's served file is transcoded by the server from its uploaded file: only the area inside its crop (MED-026) and the part inside its loop (MED-028), in H.264 (High profile), 8-bit 4:2:0 (`yuv420p`), at most 30 frames per second (a slower video keeps its rate), at constant quality 26, with its index at the start of the file so that it plays while it downloads. Its duration is the loop's length.
- **MED-035** — A video's served file is 4:3: its width is the crop's width in pixels of the video's frame as displayed (its rotation applied), at most 1,280, rounded down to a multiple of 8, and its height is three quarters of its width. It is never enlarged: 1,280 × 960 pixels at most. A crop narrower than 16 pixels of the frame is rejected (`400`, field `crop`, code `invalid_crop`).
- **MED-036** — The file uploaded for a header video is kept as its original in private storage, which no address serves (MED-044): it is the input of every re-framing (MED-030). It is copied with the media when the media is re-framed or its card duplicated (EDI-014), and deleted with the media (MED-018) and with its card (MED-019).
- **MED-037** — With a video's served file, the server makes its edit copy: the whole frame and the whole video, its longer side reduced to 960 pixels when it is longer, in H.264 with its index at the start of the file. The edit copy is the video's source (MED-025, MED-031): the dashboard plays it and draws the frames of the video crop dialog from it (EDI-034).
- **MED-038** — Neither the served file nor the edit copy of a video carries a sound track or the metadata of the uploaded file (location, dates, device): only the uploaded file's first video stream is kept.
- **MED-039** — The server processes one video at a time. An upload or a re-framing of a video whose processing, waiting included, lasts more than 120 seconds is abandoned without storing anything (`503 video_processing_timeout`). A video the server cannot read is rejected with `400`, field `file`, code `video_unreadable`; a video one of whose sides, as displayed, is longer than 4,096 pixels is rejected with `400`, field `file`, code `video_too_large`.
- **MED-040** — A video is accepted only if its first video stream is H.264, H.265 (HEVC), VP9 or AV1; any other video is rejected with `415 unsupported_media_type`.
- **MED-041** — The API refuses to start when it cannot run its video tools (`ffmpeg` and `ffprobe`, found at `FFMPEG_PATH` and `FFPROBE_PATH`, `ffmpeg` and `ffprobe` on the `PATH` by default) or when `ffmpeg` has no H.264 encoder (`libx264`), with a message that names the missing tool and how to install it.

## Storage and delivery

- **MED-009** — Media storage is S3-compatible storage by default, or the local disk when configured so (`MEDIA_STORAGE=local`), with no code change. Development, the end-to-end tests and production use S3-compatible storage.
- **MED-010** — In local disk mode, the API serves `/media/*` with long cache headers and versioned file names, behind any reverse proxy and without sharing a volume with it.
- **MED-011** — In S3 mode, media is served from the public address of a public bucket (`MEDIA_PUBLIC_BASE_URL`), on an origin different from the application's (MED-042).
- **MED-016** — A media file is never modified: replacing a media creates a new file, under a new name. `/media/*` is served, and every file of the public bucket is stored (MED-043), with the header `Cache-Control: public, max-age=31536000, immutable`.
- **MED-017** — Media files answer partial requests (`Range` header, `206` response), without which iOS does not play videos: `/media/*` in local disk mode, the public bucket in S3 mode.
- **MED-018** — A media uploaded from the editor is attached to the card only on save (see EDI-006). Media uploaded but not kept is deleted on the card's next save, and a replaced or removed media is deleted from storage, its private original included (MED-036).
- **MED-019** — Deleting a card deletes its media from storage, their private originals included (MED-036).
- **MED-020** — Only a card's owner can upload media to it or remove media from it (see ACC-017).
- **MED-023** — In local disk mode, `/media/cards/<card>/…` answers 404 when the card is not served (see LNK-026), which is checked on every request. The media URLs received by the dashboard and the support page carry a signature valid for at least 24 hours, which makes them readable even when the card is not served (see LNK-008 and ADM-013); as an exception to MED-016, they are served with `Cache-Control: private, max-age=86400`. Copies already cached by visitors are not recalled.
- **MED-024** — In S3 mode, the files of a card that is not served stay readable at their bucket URL, which cannot be guessed: v1 does not cut off their delivery. They disappear when the media is replaced or removed (MED-018) or when the card is deleted (MED-019).
- **MED-042** — In S3 mode, the API refuses to start when `MEDIA_PUBLIC_BASE_URL` has the same origin (scheme, host and port) as `PUBLIC_BASE_URL`: media files are never served from the application's origin.
- **MED-043** — In S3 mode, every file of the public bucket is stored with its exact content type (`image/webp`, `image/jpeg` or `video/mp4`), the cache policy of MED-016 and `Content-Disposition: inline`, which the bucket sends back when it serves the file.
- **MED-044** — In S3 mode, private originals (MED-036) are stored in a second bucket (`MEDIA_S3_PRIVATE_BUCKET`, on the same endpoint, in the same region and with the same keys as the public bucket) that has no public address. In local disk mode, they are stored under `private/` in the media directory, which `/media/*` never serves.
- **MED-045** — In S3 mode, the public bucket answers cross-origin `GET` and `HEAD` requests from the application's origin (`PUBLIC_BASE_URL`), and from no other origin, so that the dashboard can draw the frames of a video (EDI-034).
- **MED-046** — In local disk mode, every `/media/*` response carries `X-Content-Type-Options: nosniff`, `Content-Disposition: inline` and `Content-Security-Policy: sandbox; default-src 'none'`, so that a file opened on its own runs nothing in the application's origin.

## Framing

- **MED-025** — The server keeps the whole image of each image media, called its source: the uploaded image turned the right way up (MED-014), stripped of its metadata (MED-007) and re-encoded in WebP, its longer side reduced to 4,096 pixels when it is longer. The uploaded image bytes themselves are never stored. A video's source is its edit copy (MED-037); its uploaded file is kept privately as its original (MED-036).
- **MED-026** — A crop is a rectangle `{x, y, width, height}` given in proportions of the source, from 0 to 1: x and y are at least 0, width and height are more than 0, x + width and y + height are at most 1. Measured in pixels of the source (for a video, of its frame as displayed, its rotation applied), it is 4:3 for the header and square for the profile photo, within 1%. Any other crop is rejected (`400`, field `crop`, code `invalid_crop`). When an upload carries no crop, the server takes the largest centered rectangle of the right shape.
- **MED-027** — The files shown on the card (MED-015) are cut by the server from the source along the crop, so that the media can be re-framed later (MED-030).
- **MED-028** — A header video carries a framing: its crop (MED-026), its loop `{start, end}` and its poster time, in seconds. The loop satisfies 0 ≤ start < end ≤ the video's duration as the server read it (MED-013), and end − start ≥ 1 unless the loop is the whole video; otherwise the upload is rejected (`400`, field `loop`, code `invalid_loop`). The poster time lies between 0 and the duration (field `poster_time`, code `invalid_poster_time`). Without them, the loop is the whole video and the poster time is 0.
- **MED-029** — A video's placeholder image is the frame the server extracted at its poster time (MED-003), cut by the server along the video's crop like a header image (MED-027).
- **MED-030** — Re-framing a media (a new crop and, for a video, a new loop or poster time) creates a new media: an image's files are cut again from its source; a video is transcoded again from its private original (MED-034, MED-036), with a placeholder image extracted again (MED-003), and keeps the same edit copy under a new name (MED-031). The previous media and its files are not modified (MED-016). Like an upload, the new media is shown on the card only once a save attaches it (MED-018). A media uploaded before plan 6, which has no source, and a video uploaded before plan 7, which has no original, cannot be re-framed (`409 media_not_reframable`): they must be replaced. The dashboard receives no source for them, so it does not offer to re-frame them.
- **MED-031** — A source (an image's source or a video's edit copy) is stored under a file name that cannot be guessed (it carries a random token, different for every media) and is only given to the card's owner in the dashboard, to re-frame the media: in local disk mode through a signed address (MED-023), in S3 mode at its bucket address, which cannot be derived from the addresses of the media's public files (see MED-024). It is never part of the public page, of the vCard or of the support views, and in local disk mode `/media/*` refuses it (404) without a valid signature, even when the card is served.
- **MED-032** — The public page shows a header video's served file as it is, covering the 4:3 header: its crop and its loop are already in the file (MED-034), which plays from its start and loops over its whole length (PUB-005).
- **MED-033** — A media uploaded before plan 6 has no crop: its image or its video covers the 4:3 header, centered, and a video loops over its whole length. A video uploaded before plan 7 is shown the same way: its file as uploaded covers the header, centered, and loops over its whole length; its stored crop and loop are not applied, and its placeholder image stays the one cut along its crop.

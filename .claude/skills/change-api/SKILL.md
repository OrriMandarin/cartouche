# Changer l'API

Précondition : la règle de spec existe (skill `update-spec`). Ordre à suivre, chaque étape avec son test (TDD : test qui échoue d'abord).

Dossiers : `backend/domain/` (`cartouche-domain`, logique pure), `backend/server/` (`cartouche-api`). Poste local : `source ~/.cargo/env`, `export PATH="$HOME/.local/bin:$PATH"`, base de dev lancée (`make dev-db`) et `DATABASE_URL` exporté pour `cargo test`.

1. **Migration SQLx** : `backend/server/migrations/NNNN_<nom>.sql` (prochain numéro après `ls backend/server/migrations`). Les migrations appliquées ne se modifient jamais : on en ajoute une. Elles s'appliquent au démarrage de l'API et dans `#[sqlx::test(migrations = "./migrations")]`.
2. **Nouvelles tables dans `RESET_TABLES`** (`backend/server/src/test_support/seed.rs`) : sinon `reset` ne les vide pas et les tests e2e se polluent. Une table qui référence une autre se met avant elle ou reste couverte par `truncate … cascade`.
3. **Fonctions `db/`** (`backend/server/src/db/<table>.rs`, déclarées dans `db/mod.rs`) : requêtes SQLx avec les macros `sqlx::query!` / `query_as!` (vérifiées à la compilation contre le cache `backend/.sqlx/`), puis `make sqlx-prepare` et commiter le diff de `.sqlx/` ; sinon la compilation échoue (« no cached data for this query ») et `make sqlx-check` aussi. **Toute lecture ou écriture de données utilisateur prend l'identifiant du propriétaire** et le met dans la clause `where` ; aucune fonction sans propriétaire sur des données utilisateur. Les seules exceptions sont documentées **en tête du fichier** : `db/public_cards.rs` et `db/admin_cards.rs`, les fonctions `*_public` de `db/events.rs` (lecture d'un événement d'une carte déjà résolue par son slug) et `lock_device`, `count_for_device`, `insert` de `db/leads.rs` (écriture d'un prospect anonyme, toujours pour un événement résolu par `events::find_public`). Toute nouvelle exception se documente de la même façon et se justifie en revue.
4. **Logique métier dans `cartouche-domain`** : règles, validation, normalisation (`normalize` : NFC + trim). Le handler ne contient aucune logique. Toute dépendance externe (horloge, jeton, stockage, e-mail) passe par un trait.
5. **Route** (`backend/server/src/routes/<nom>.rs`, déclarée dans `routes/mod.rs`) : le handler lit la requête, appelle le domaine et `db/`, formate la réponse. Annoter avec `#[utoipa::path(...)]` (méthode, `path`, `summary`, `description`, `tag`, `security(("bearer" = []))`, **toutes** les réponses y compris 401/403/500 avec `ErrorBody`) et dériver `ToSchema` sur les types. Les erreurs passent par `ApiError` (`src/error.rs`, forme `{"error":{"code","message","request_id"}}`) ; un nouveau code d'erreur = une nouvelle variante. Une erreur de saisie est `ApiError::Validation(Vec<FieldError>)` : `400 validation_failed` avec `"fields":[{"field","code"}]` (chemins comme `content.email`, `links[3].url` ; le champ `fields` n'existe que pour ce code). Un corps `multipart/form-data` (envoi de média) se lit avec l'extracteur `ApiMultipart` (`src/extract.rs`) : `413 payload_too_large` et `415 unsupported_media_type` y sont déjà traduits. Brancher ensuite la route dans `src/app.rs` et ajouter le handler à `paths(...)` dans `src/openapi.rs` (nouveaux schémas dans `components(schemas(...))`, nouveau tag dans `tags(...)`). Les routes `/api/test/*` ne sont **jamais** dans l'OpenAPI. Les routes du propriétaire prennent l'extracteur `ApprovedUser` ; les routes publiques ne prennent aucun jeton et portent le tag `public`.
6. **Tests d'intégration** (`backend/server/tests/<sujet>.rs`, harnais `tests/common`) : `// spec: XXX-NNN` avant chaque test. Couvrir au minimum : cas nominal, 401 sans jeton, statut de compte non approuvé (403) si la route exige un compte approuvé, isolation entre propriétaires.
   ```bash
   cd backend && cargo test -p cartouche-api --all-features --test <fichier>
   ```
7. **Régénérer le contrat et le client** : `make openapi` (écrit `frontend/api-client/openapi.json` puis `src/schema.d.ts`). Ne jamais éditer ces fichiers à la main ; commiter leur diff. Sans cela, le test `openapi_is_up_to_date` échoue (« OpenAPI drift »).
8. **Frontend** : utiliser les types générés de `@cartouche/api-client` via `frontend/web/src/lib/api.ts` ; logique dans `frontend/web/src/lib`, composants sans logique métier ; tout texte dans `frontend/web/messages/fr.json` (aucun texte en dur). Tests vitest avec la règle dans le nom, et un test e2e (`frontend/e2e/tests/`) si un parcours utilisateur change.
9. **Vérifier** : `make lint test`, puis `make e2e` si l'interface est touchée.

## Route publique d'un objet rattaché à une carte (événements, formulaire)

Modèles : `routes/public_events.rs` et `routes/public_cards.rs`.

- **Résoudre la carte par `serve_card(state, slug)`** (`routes/public_cards.rs`), jamais par une requête maison : un ancien slug ou un slug écrit avec des capitales atteint la carte comme le slug courant. Une carte non servie (désactivée, supprimée, propriétaire suspendu) répond `410 card_inactive`, un slug jamais attribué `404 not_found`. Un objet inconnu ou d'une autre carte est aussi `404 not_found` (utiliser `events::find_public(db, card.id, event_id)`, jamais la lecture du propriétaire).
- **Ne rien divulguer** : une vue publique ne contient jamais le code d'accès (ni en clair, ni haché), même pour un événement à code ; les champs, la description et le consentement d'un tel événement ne sortent qu'après un code correct. Écrire le test qui cherche le code dans le HTML et dans chaque réponse de `/api/public/*`.
- **Ne rien journaliser des saisies du prospect.** Les corps qui portent des réponses ou un code (`UnlockBody`, `LeadSubmission`) ne dérivent **pas** `Debug` (commentaire `// No Debug` à l'appui) ; l'extracteur `ApiJson` ne journalise que le statut du rejet, car le texte de rejet de serde peut citer les valeurs. Aucun `tracing::…` ne reçoit une réponse, un code ou une adresse e-mail.
- **Limite par IP** : ajouter un `ClientIp(ip)` au handler (`src/client_ip.rs` : la n-ième adresse de `X-Forwarded-For` en partant de la droite, n = `TRUSTED_PROXY_HOPS`, ABU-008) et passer par `state.rate_limiter` (trait `RateLimiter`, `src/rate_limit.rs`). Chaque compteur est un `Bucket` (`LeadSubmission`, `FailedAccessCode`) dont la limite vient du domaine. `hit` compte et vérifie en une étape (ce qui compte même un envoi refusé) ; `check` puis `record` quand seul un échec compte (un code faux). Un refus est `ApiError::RateLimited { retry_after_secs }` : `429 rate_limited` avec l'en-tête `Retry-After`. Un nouveau compteur = une variante de `Bucket` et sa constante dans le domaine. Dans les tests, `app.request_from("203.0.113.7", method, path, token, json)` simule l'adresse d'un client derrière le proxy ; `POST /api/test/reset` remet les compteurs à zéro.
- **L'heure vient toujours de `state.clock.now()`** (grâce d'envoi, fenêtre de la limite par IP, date du jour d'une date de naissance : `clock.now().date_naive()`), jamais de `Utc::now()` dans `server/src` hors `main.rs` et `bin/`. C'est ce qui permet de figer l'horloge dans les tests.
- **Adresses des médias** (`views::Audience`) : `Audience::Dashboard(now)` pour les vues du propriétaire et du support (adresses signées, lisibles même si la carte n'est pas servie, MED-023), `Audience::Public` pour le public (adresses simples, `404` si la carte n'est pas servie). Une vue construite pour le mauvais public est un bug de confidentialité ou une image cassée.
- **Concurrence** : deux requêtes simultanées ne doivent pas franchir une limite par un test-puis-écriture. Prendre un verrou dans la transaction : celui de la carte (`cards::lock_for_owner`, ou `events::lock_card_of_event` qui le prend en premier, pour la limite d'événements simultanés) ou un verrou consultatif (`leads::lock_device`, `pg_advisory_xact_lock`, pour la limite par appareil), puis relire et décider. Le test lance les requêtes ensemble avec `futures_util::future::join_all` et compte les statuts (`tests/events.rs`, `tests/leads_submit.rs`).
- **Codes d'erreur ajoutés** (variantes d'`ApiError`) : `too_many_simultaneous_events`, `event_not_running`, `event_closed`, `form_changed`, `device_limit_reached` (409), `invalid_access_code` (403), `rate_limited` (429, `Retry-After`) ; `card_inactive` (410) et `not_found` (404) sont réutilisés. Codes de champ de `validation_failed` : `end_before_start`, `out_of_range`, `no_fields`, `too_many_fields`, `duplicate_field_id`, `too_few_options`, `too_many_options`, `duplicate_option`, `invalid_date`, `invalid_number`, `invalid_choice`, `invalid_value`, en plus de `required`, `too_long`, `invalid_email`, `invalid_phone`. Les chemins de champ ressemblent à `custom_fields[2].options[1]` ou `answers.address.city`.
- **Variables d'environnement** : une nouvelle variable se lit dans `config`, se documente dans `.env.example` (sans accents) et dans la skill `dev-env`. Celles du plan 3 : `MAX_SIMULTANEOUS_EVENTS` (défaut 3, entier ≥ 1) et `TRUSTED_PROXY_HOPS` (défaut 1, entier de 0 à 10).

Stockage de fichiers (médias) : la base fait foi. Écrire les fichiers via `MediaService`, valider la transaction **avant** de supprimer des fichiers, et nettoyer le stockage au mieux (best effort) après le `commit` : un fichier qui ne part pas est journalisé et laissé, la requête réussit quand même. En cas d'échec en cours de route, retirer les fichiers déjà écrits.

Pièges : jamais de SQL construit par concaténation d'entrées ; normaliser (NFC + trim) toute chaîne reçue avant stockage ; ne rien mettre dans le jeton que la base doit relire (le statut est relu à chaque requête, ACC-005).
